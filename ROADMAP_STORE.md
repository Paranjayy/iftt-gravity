# 🛒 Roadmap: General-Public Raycast Store Release

> **Status**: PREP ONLY — no publishing until user signs off.
> Goal: Tame `gravity-hub` into a general-purpose Raycast extension that
> anyone can install and use against their own hub, without exposing your
> personal Pi credentials, IPs, or Telegram bot.
>
> **Hard rule during prep:** existing features MUST NOT regress. All
> changes are additive or behind a feature flag that defaults to current
> behavior for the local user. Nothing destructive — no renames, no
> deletions, no behavior changes without explicit user sign-off.

---

## 🎯 North star

A user installs the extension, opens the preferences, pastes a **Hub URL**
and (optionally) a few API keys, and gets a working mission-control for
their home — AC, lights, scenes, schedules, energy — without writing
code, cloning a repo, or running a backend service they don't understand.

The current `gravity-hub` is your personal fork; this is the
"boring-public" version that's safe to publish.

> *"gravity hub is cringe right lol"*

Agreed. Current name ties us to the personal `iftt` repo and the
"gravity" theme, which means nothing to a public user. Options:

**My pick:** `homepulse` — distinctive, fits the existing "Pulse" theme
(Hub Pulse, Pulse Check, etc.), and the user picked it themselves.

Final decision is yours; nothing renames until you say so.

## 🧭 Guiding principles (in priority order)

1. **No regression.** The local user's flow (Control House, Hub Pulse,
   Quick Scene, schedules, etc.) must keep working bit-for-bit.
2. **Preferences over hardcoded values.** Every `127.0.0.1`, every
   `192.168.x.x`, every API key, every Telegram token must be a
   Raycast preference with a sane default that matches current behavior.
3. **Optional features.** SmartThings, Solis, Telegram send — each
   must be guarded by a "do you have this set up?" preference. If no,
   the relevant section is hidden, not broken.
4. **Self-explanatory errors.** No more "Hub Offline" without a next
   step. The new `<HubOfflineDetail/>` component (already shipped) is
   the template; apply it to every offline path.
5. **No bundled credentials.** `config.json` (Telegram token, miraie
   password, router admin) MUST NEVER touch the public extension.
   The extension talks to a *user-configured* bot URL, period.

## 🚧 Implementation phases (additive, no regression)

### Phase A: Hub URL preference (1-2 hours, ZERO regression)

Add a `hubUrl` preference (default `http://127.0.0.1:3030`). Add a
`getHubUrl()` helper in a new `src/lib/config.ts`. **For now**, only
the *one command* you choose to test it on reads from the helper.
Everything else keeps using the hardcoded URL.

**No global swap.** Wait until the helper is proven, then sweep.

**Validation:** the local user sees no change because the default
matches the current value.

### Phase B: Public-readme + LICENSE (1 hour, ZERO regression)

Write `raycast-ext/README.md` aimed at a public user. Add `LICENSE`
file. Update `CHANGELOG.md` with a "v1.3.0 — Public store prep" entry.

The README can be written from your notes + the existing
`CHANGELOG.md` + the command registry.

### Phase C: Naming + icon reskin (separate commit, visible change)

When you pick the final name, do the swap in one commit:
- `name`, `title`, `description` in `package.json`
- All `import` paths in `src/`
- All `title:` strings
- The master icon (re-run `make-command-icons.py` with new base)
- The bot name in any UI strings

This is the one commit that's visible; everything before/after is
invisible to you.

### Phase D: Public reference bot (separate repo, opt-in)

Spin out a stripped bot template as `iftt-public-bot/` (or a separate
repo). The extension doesn't change. The README links to it.

This decouples the extension from your personal bot.

### Phase E: Sweep — every command reads `getHubUrl()` (additive)

Now that the helper is proven, sweep through `src/`. Each command
reads `getHubUrl()` instead of the literal. Each command's offline
state uses `<HubOfflineDetail/>` with a retry callback.

**Regression risk: low** because the default value matches current
behavior. Run `bun run dev` and click through every command after.

### Phase F: Optional features guarded by preferences (additive)

Each optional section reads its preference; if unset, the section
hides. SmartThings, Solis, Telegram — same pattern.

**Regression risk: low** because the local user already has the
values set (in their existing preferences).

## 🧪 Test plan for Phase E (the sweep)

After every command is migrated:

1. Set `hubUrl` preference to `http://127.0.0.1:3030` (default).
   → All commands work as before.
2. Set `hubUrl` to `http://my-public-bot.example.com`.
   → All commands work against the new URL.
3. Set `hubUrl` to `http://127.0.0.1:9999` (deliberately wrong).
   → All commands show `<HubOfflineDetail/>` with a retry.
4. Clear `hubUrl` (empty string).
   → Falls back to `http://127.0.0.1:3030`.

If any of these fail, the command wasn't fully migrated.
